# Agent 评测体系设计

状态：设计提案  
适用范围：`typescript/src/` Harness、Electron 桌面运行时及其发布流程

## 目标

评测要回答四个不同的问题：Agent 是否完成任务、是否按权限和约束行动、运行是否稳定、完成任务花费多少时间和资源。结果按能力类别和风险等级呈现，不压成一个无法诊断的总分。

体系需要支持：

- 用固定数据集发现代码、提示词、工具和模型配置变更造成的回归。
- 通过真实的 `AgentRuntime.run()` 执行任务，而不是只给预先生成的答案打分。
- 从 Trace 和运行预算中获取调用次数、失败、取消、Token 与耗时数据。
- 验证工具调用、最终工作区状态、引用依据和权限边界。
- 对随机性、评测数据变化、评判器版本和模型版本保留可复现记录。
- 默认在本机和隔离工作区运行；用户对话和原始 Trace 不得自动上传。

## 当前实现与差距

`typescript/src/evaluation_service.ts` 当前接受 `cases` 与 `outputs`，通过字符串完全匹配计算正确率，通过引用子串匹配计算 grounding rate，并持久化通过或阻断状态。`evaluation-ci` Feature 暴露 `evaluation_gate` 和 `evaluation_status`。这适合作为一个有界的确定性评分和记录服务。

它目前没有执行 Agent，也不能证明传入的 `outputs` 是实际运行结果。若被测 Agent 自己调用 Gate，它可以自行提供答案；若把隐藏期望值传入模型上下文，评测数据也会泄漏。因此，完整评测的调度、运行和判分必须由 Agent 之外的评测控制器负责。现有 Gate 可以继续作为评分记录层，不能单独作为端到端能力评测。

当前架构已经提供可复用的边界：`AgentRuntime.run()` 接受 workspace、provider、model、权限模式、AbortSignal、预算和事件回调；`AgentRuntimeDependencies` 支持注入 Provider；`TraceSummary` 包含状态、耗时、调用计数和 Token 用量。Trace 摘要有意不保存提示词、工具参数、工具输出和凭据，评测应保持这一隐私默认值。

## 评测分层

| 层级 | 目的 | 环境与执行方式 | 触发时机 |
| --- | --- | --- | --- |
| L0 契约检查 | 校验数据集、评判器、工具策略、预算和记录格式 | 不启动模型；纯确定性 | 每个 PR |
| L1 组件回归 | 检查单个工具、上下文压缩、记忆、引用和权限规则 | 临时目录、固定输入、Stub | 每个 PR |
| L2 Harness 端到端 | 检查完整主循环、工具往返、失败恢复、取消和结果状态 | `AgentRuntime` + 脚本化假 Provider + 虚拟工具或临时工作区 | 每个 PR；不产生 API 费用 |
| L3 模型能力评测 | 比较指定 Provider/模型在代表性任务上的成功率、方差和成本 | 显式配置真实 Provider；固定模型、提示和工具版本；多随机种子 | 夜间或发布候选 |
| L4 发布验收 | 检查真实桌面流程、权限确认、流式输出、取消和升级行为 | 人工验收或明确批准的本地冒烟场景 | 发布前 |
| L5 线上质量观察 | 发现部署后的失败类型与能力漂移 | 仅在用户明确启用后收集最小化、脱敏指标 | 持续观察 |

L0–L2 是快速、稳定、离线的常规门禁。L3 不应在普通 PR 中隐式调用真实模型或产生账单。L5 默认关闭，不上传提示词、用户文件、工具参数或原始输出。

## 任务数据集

数据集采用有版本、可校验的 JSONL 或 JSON 格式。每个用例包含任务输入、隔离环境、约束、预算、评判规则和风险标签；期望答案和隐藏断言只由评测器读取，不进入 Agent 的提示词、工具参数或普通 Trace。

建议的核心字段：

```json
{
  "schemaVersion": 1,
  "id": "repo-fix-004",
  "tags": ["coding", "multi-step", "regression"],
  "risk": "ordinary",
  "input": "修复 fixture 项目中的配置读取错误，并说明验证结果。",
  "fixture": "fixtures/repo-fix-004",
  "budget": { "iterations": 12, "toolCalls": 20, "outputChars": 30000 },
  "seed": 17,
  "assertions": {
    "finalState": [{ "path": "src/config.ts", "sha256": "..." }],
    "requiredTools": ["read_file", "edit_file"],
    "forbiddenTools": ["mcp_call"],
    "mustDeny": [],
    "rubric": "完成修复，且没有改动无关文件"
  }
}
```

数据集元信息另外记录 `datasetId`、版本、内容 SHA-256、创建时间、来源与许可、维护人、标签定义及评判器版本。用例按能力切片维护，初始覆盖：

- 直接问答、指令遵循、格式约束和澄清行为。
- 文件读取与修改、代码修复、多文件任务、测试结果核验。
- 工具选择、参数正确性、工具错误恢复、无效工具调用避免。
- 检索、PDF/图像输入、引用正确性和证据不足时的拒答。
- 长上下文、压缩前后事实保留、跨轮记忆与任务恢复。
- 权限请求、路径边界、危险命令拒绝、提示注入和秘密泄漏。
- 超时、Provider 错误、取消传播、预算耗尽和子进程清理。

至少维护三个集合：公开开发集用于迭代；固定回归集用于 PR 和夜间比较；保留集用于发布验收。保留集的期望结果不得进入 Agent 可访问的目录或 Prompt。新失败用例经人工核验后加入回归集，并提升数据集版本。

## 评测运行器

新增一个 Harness 外部的运行层，例如 `typescript/src/evaluation/runner.ts`。它读取已校验的数据集，在每个用例的独立临时 workspace 和 session 中调用 `AgentRuntime.run()`，收集最终回答、事件、TraceSummary、最终状态快照及资源指标，再把这些实际结果交给评判器。评测控制器不得作为被测 Agent 的工具，也不得把候选答案交由 Agent 自行填报。

运行器必须：

1. 固定并记录 Agent 代码版本、数据集哈希、Provider、模型、提示版本、工具集版本、运行预算、随机种子和评判器版本。
2. 每个用例使用新建的临时 workspace；只复制声明的 Fixture，禁止访问用户工作区。
3. L2 使用脚本化 Provider 和工具替身，所有回复、错误、延迟及工具状态可重复。
4. 默认禁用真实网络、MCP、后台任务、计划任务和宿主机 Shell。确需覆盖这些能力时，使用独立受限环境和单独的数据集。
5. 有界并发执行；单用例和整组都有超时、迭代数、工具调用数、输出量及取消上限。
6. 记录取消是否传到 Provider、工具和子进程，并检查用例结束后无残留进程或后台工作。
7. 对真实模型运行显式显示 Provider、模型、预计用例数和费用口径；真实运行只能由单独的 CLI/任务触发，不由聊天工具隐式启动。

评测 ask 权限模式需要可控的权限决策替身，验证“应请求、获批、拒绝”三类结果；该替身只用于隔离评测。不得为了自动化把权限模式改为 `full` 或放宽生产权限检查。必要时为 Runtime 增加显式注入的 `PermissionDecisionProvider`，生产默认实现仍调用现有权限界面。

## 评判器与指标

评判器分为确定性和辅助性两类。确定性结果是发布门禁依据；LLM Judge 只能生成辅助评分与复核建议，不能独立批准高风险发布。

| 维度 | 首选判定方式 | 汇总指标 |
| --- | --- | --- |
| 任务完成 | 最终状态、补丁、结构化字段或业务状态断言 | 成功率、按能力/风险分层的成功率 |
| 答案正确 | 精确值、规范化值、JSON Schema、可验证断言；开放式回答才用校准过的 rubric | 正确率、拒答准确率、复核率 |
| 证据质量 | 引用 ID/URL 与来源集合比对；引用段落支持断言的确定性规则或人工复核 | 引用精确率、召回率、无依据主张率 |
| 工具行为 | 从真实事件流检查工具名、参数、顺序、次数和最终副作用 | 必需调用完成率、错误调用率、无效副作用数 |
| 安全与权限 | 对应允许/拒绝断言、工作区边界和秘密扫描 | 严重违规数、拒绝正确率、越界副作用数 |
| 稳定性 | 同一用例多个种子重跑；包含取消、重试和工具失败场景 | 单次成功率、pass^k、失败率、结果方差 |
| 效率 | Trace 与 Provider 返回的 usage；实际值和估算值分开 | p50/p95 延迟、请求/工具数、实际 Token、估算 Token、费用/成功任务 |

结构化任务优先比较最终状态，而非答案措辞。文本任务的精确匹配只用于答案本身确有唯一值的场景；引用子串出现不能证明引用支持结论，应检查来源身份和引用片段。实际 Provider 用量缺失时标记为 `unknown`，不得用字符估算冒充计费 Token。

随机运行分别报告 `pass@k`（k 次中至少成功一次）和 `pass^k`（k 次全部成功）；发布可靠性以 `pass^k` 或成功率置信区间为主，不能只展示最优一次。小样本按用例切片给置信区间；同时给出失败用例 ID 和错误类别，不只给总百分比。

## 结果记录与门禁

评测运行记录应把“运行清单、每例结果、聚合结果、发布判定”分开，建议的数据结构：

- `runId`、时间、代码提交、数据集 ID/版本/哈希、Provider/模型、提示/工具版本、评判器版本和运行种子。
- 每例的状态、分维度分数、错误类别、Trace ID、耗时、Provider 请求数、工具调用数、实际 Token/费用（若可用）及估算值。
- 聚合数据包括总成功率、分层切片、置信区间、稳定性、p50/p95、费用和相对基线变化。
- Gate 状态至少支持 `passed`、`blocked`、`review_required`、`insufficient_data`。样本缺失、评判器失败或 Provider usage 未提供时不能静默当作通过。

原有 `EvaluationRecord` 可继续保存精简的评分和复核队列。新增字段应通过显式 `schemaVersion` 迁移，复用原子写入、工作区隔离、租户约束和幂等键。默认不把原始 Prompt、候选输出、工具参数或文件内容写入持久化记录；需要人工诊断时由用户在本机显式导出脱敏工件。

门禁先设不可豁免的安全条件，再设质量和资源条件：

1. 任一严重权限绕过、越出临时 workspace 的写入、凭据泄漏或取消后残留任务都阻断发布。
2. 关键能力切片不得低于其基线底线；整体与切片回归应结合置信区间和最小样本数判断。
3. 费用、p95 延迟、Provider 失败率不得超过经基线测得的预算。
4. 不稳定用例进入 `review_required`；只有所有指定重试都完成后才能计算可靠性，不能只保留最好结果。
5. 评判器或数据集校验失败、用量证据不足、执行未完成时返回 `insufficient_data` 或阻断，不当作通过。

当前 0.95 阈值适用于既有小型精确匹配 Gate。端到端任务应按风险和能力切片建立基线后设置阈值，不应直接复制该阈值作为全 Agent 通过线。

## 接入仓库的建议结构

```text
typescript/src/evaluation/
  dataset.ts       # 数据集类型、版本、Schema 校验和哈希
  runner.ts        # 临时工作区、Runtime 调用、并发和取消
  evaluators.ts    # 最终状态、答案、引用、工具、安全断言
  aggregate.ts     # 切片、重试、置信区间和基线比较
  report.ts        # 精简 JSON/Markdown 报告
typescript/evaluation/
  datasets/        # 可公开的版本化评测数据
  fixtures/        # 合成工作区和虚拟工具状态
  expected/        # 受限保存的判分断言；不加入 Prompt 和工具输入
```

生产模块仍只从 `typescript/src/` 实现，不导入 `stages/`。第一阶段不需要新增 UI：通过 CLI 生成 JSON/Markdown 报告，并保留现有 `evaluation_status` 用于查询精简门禁记录。稳定后再考虑桌面报告视图。

建议命令：

- `deno task eval:contracts`：数据、评判器和记录格式校验。
- `deno task eval:smoke`：少量 L2 假 Provider 用例，无网络、无费用。
- `deno task eval:nightly`：代表性模型回归，可配置 Provider 和多种子。
- `deno task eval:release`：固定保留集、完整安全用例和资源门禁。

`evaluation_gate` 继续接收评测控制器已经判定的结果，用于记录、幂等查询和阻断信号；不应负责启动模型，也不能被当作模型真实性或质量的证明。CLI 与 CI 才是发布 Gate 的权威调用方。

## 推进阶段

1. **定义数据合同**：补 schema 版本、数据集校验、哈希、标签和规范化错误类别；明确期望字段在 Runner 与 Agent 之间隔离。
2. **建立离线闭环**：实现假 Provider 端到端 Runner、临时 workspace 和确定性评判器；先覆盖工具往返、任务完成、取消、权限拒绝和失败恢复。
3. **接入运行证据**：从 `TraceSummary` 汇总状态、耗时、调用数和 Token；提供 JSON/Markdown 报告与失败复核工件。
4. **建立基线**：选择固定 Provider/模型/提示组合，执行代表性多种子评测，测量成功率、波动、费用和 p95 后再定门槛。
5. **发布与夜间门禁**：把低成本 L2 放在 PR，把真实模型评测放在显式夜间/发布任务；保留集和安全严重违规门禁独立管理。
6. **线上反馈（可选）**：先定义本机指标和明确的数据导出流程；只有用户明确启用后才收集脱敏样本，并建立人工复核和删除机制。

## 外部基准的使用

外部基准用来补充能力覆盖，不替代项目自己的工作流数据。AgentBench 将评测放在多个交互环境中；GAIA 覆盖需要推理、多模态、浏览和工具使用的助手任务；τ-bench 强调 Agent、模拟用户与业务状态之间的多轮交互，并使用重复运行衡量稳定性。迁移任何公开数据集前，需核对许可、运行环境和任务是否对应本产品能力；项目发布分数必须记录基准版本、系统配置和执行预算。
