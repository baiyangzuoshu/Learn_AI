# s01：最小 Agent Loop

源码：[s01_agent_loop.ts](../s01_agent_loop.ts)

## 学习目标

- 理解系统提示、用户消息和模型回答的基本关系。
- 理解模型如何通过 `tool_calls` 请求本地执行 `bash`。
- 掌握“模型 → 工具 → 工具结果 → 模型”的循环。

## 核心机制

`agentLoop()` 组装消息并调用
Provider。模型返回普通文本时结束；返回工具调用时，本地执行命令，将结果作为 `role: "tool"`
消息回填，再次请求模型。大模型只负责决定动作，真正的 Shell 操作由 Deno 进程执行。

## 为什么一个循环就够了

普通聊天只执行一次“请求 →
回答”，模型即使知道应该查看文件，也没有办法真正查看。工具调用把模型输出扩展成动作请求；Harness
执行动作并把观察放回历史，模型便能依据真实环境继续判断，而不是猜测。代码不需要用规则树替模型规划工作流。

沿源码追踪一次执行：`systemPrompt()` 声明工作区；`TOOLS` 用 JSON Schema 描述 `bash`；`agentLoop()`
调用 Provider 并保存 assistant 响应；遇到 `tool_calls` 时由 `runBash()` 执行，结果以对应调用 ID 和
`role: "tool"` 回填；没有工具调用时返回最终文本。

```text
user → model → bash({command}) → tool result → model → final answer
```

模型只生成工具名与 JSON 参数，真正的 Shell 权限始终在 Deno
进程手中。输出截断体现了“观察也必须有界”，但本课尚未处理命令风险、循环次数和总时长，后续会分别补齐。

## 运行与观察

```sh
deno task s01
```

尝试输入“列出当前目录”。观察模型生成的工具参数，以及工具输出如何影响下一轮回答。

## 练习

1. 打印 Provider 调用轮次，验证一次工具动作为什么至少产生两次模型请求。
2. 增加最大轮次限制，并思考网络失败和命令失败应分别在哪一层处理。
3. 暂时把 `bash` 限制为只读命令，观察能力范围如何改变模型策略。
