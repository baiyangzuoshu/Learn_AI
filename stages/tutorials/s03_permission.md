# s03：权限审批

源码：[s03_permission.ts](../s03_permission.ts)

## 学习目标

- 区分 `ask`、`auto` 和 `full` 三种权限模式。
- 理解用户审批与硬拒绝规则的不同职责。
- 学会按工具副作用分类权限。

## 核心机制

工具执行前构造 `ToolRequest` 并进行授权。`ask` 对变更操作询问用户，`auto` 允许普通工作区操作，`full`
只能由用户显式开启。危险命令的硬拒绝是最后防线，不能替代审批。

## 权限不是一个布尔值

同一个 `bash` 既能执行只读的 `git status`，也能删除数据，因此授权对象必须是完整
`ToolRequest`，而不只是工具名。`permissionReason()`
识别副作用并生成知情审批文案；`createAuthorize()` 先应用任何模式都不能绕过的
`denyPatterns`，再处理模式差异。

| 模式   | 普通读取 | 工作区写入 | 外部或危险动作     |
| ------ | -------- | ---------- | ------------------ |
| `ask`  | 通常执行 | 请求审批   | 审批或拒绝         |
| `auto` | 执行     | 边界内执行 | 仍受安全检查       |
| `full` | 执行     | 执行       | 仅可由用户显式选择 |

硬拒绝与审批职责不同：前者表示产品不应执行，后者允许用户针对具体动作授权。`auto`
也不是无限权限，不能逃逸工作区。Shell
正则只是教学后盾，生产实现还应结合工具副作用元数据、规范化路径和外部目标，并把检查放在最接近执行的位置。

## 运行与观察

```sh
deno task s03
```

比较读取文件和写入文件的审批差异，再测试一个明显危险的 Shell 命令是否被拒绝。

## 练习

为工具增加 `read-only/mutating/external/dangerous`
元数据，替代工具名列表。为四类各设计一个请求，验证 `auto` 只自动批准工作区内的普通动作。
