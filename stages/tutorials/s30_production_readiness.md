# s30：生产就绪综合层

源码：[s30_production_readiness.ts](../s30_production_readiness.ts)

## 学习目标

- 汇总 s21–s29 的高级能力。
- 用明确控制项审计生产准备情况。
- 理解“构建成功”不等于“生产可用”。

## 核心机制

`production_readiness_check` 检查有界运行、Schema
校验、权限、秘密脱敏、Trace、回归评估、检查点和发布验证。只有全部控制项被证实才返回
`ready: true`，且仍要求目标平台原生测试。

## 上线是证据集合，不是一个布尔开关

`production_readiness_check` 要求有界运行、Schema 校验、权限、秘密脱敏、结构化 Trace、回归
Eval、检查点恢复与发布验证八项控制，并分别返回 `passed` 和
`missing`。只有调用方提供明确证据后才应把控制项设为 true。

这个检查工具本身无法证明实现正确：传入八个 true
只会展示清单逻辑。因此真实发布门禁应从自动测试、构建产物检查、安全扫描和目标平台手测读取证据，而不是接受模型自报。

高级能力之间形成闭环：s21 防止失控，s22 记录发生了什么，s23 判断行为是否达标，s24–s27
提升知识与协作质量，s28 支持恢复，s29 在证据不足时阻止盲目行动。任何一环都不能替代权限和秘密管理。

## 发布前四层证据

1. **静态层**：格式、类型、依赖边界、Schema。
2. **行为层**：单元、集成、Eval 与取消/失败测试。
3. **产物层**：真实发布包只嵌入允许文件，不包含密钥和开发配置。
4. **平台层**：在 macOS、Windows、Linux 原生验证凭据、Shell、Git、WebView 和退出清理。

跨平台构建成功只证明编译与打包，不能证明原生运行行为。

## 运行与观察

```sh
deno task s30
```

先用部分控制项运行审计，再补全控制项，比较 `passed` 与 `missing`。

## 后续方向

将 s21–s30 中验证有效的设计逐个迁移为 `src/features/` 生产模块。让 readiness
检查读取真实测试与构建产物证据；每项控制记录负责人、证据链接、验证时间和失效条件。
